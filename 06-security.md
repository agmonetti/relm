# 06 — Security: threat model and decisions

Document aimed at project maintainers. For the end-user guide, see `07-user-security.md`.

## Threat model

`relm` is a local, single-user TUI that connects to databases the user brings themselves. There's no server, no multi-tenancy, and no code that receives input from third parties beyond the keyboard. That's why the threat model is small and local:

| Threat | Risk | Current mitigation |
|---|---|---|
| Another user on the same machine reads saved passwords | High | `connections.json` with `0600` permissions (directory `0700`). Saving the password is optional. |
| Connection without TLS to a network database → MITM reads credentials and data | Medium-high | `SSL` field in PostgreSQL (`prefer` by default). MySQL/MariaDB and SQL Server don't expose a TLS option yet. |
| Accidental damage to production (`DROP`, `UPDATE` without `WHERE`, mass `DELETE`) | Medium | `Read-only` mode for SQLite. `relm` doesn't ask for confirmation (design decision). |
| Queries with sensitive data visible on screen | Low | That's the purpose of the tool; the user controls what runs. |
| Logging of queries or passwords to disk | None | No logging to file. Errors are shown on screen. |

## Design decisions and accepted tradeoffs

### Passwords in plaintext in `connections.json`

`Ctrl+S` saves the connection in `~/.config/relm/connections.json` (`0600` permissions). If the user chooses to save the password, it goes in **plaintext** in that JSON.

- **Why:** a TUI can't delegate to the system GUI in a portable way without a dependency; the OS keychain manager remains as future work.
- **Mitigation:** `0600`/`0700` permissions, optional password, and a masked field in the form.
- **Backlog:** integrate the system keychain (macOS Keychain, libsecret, Windows Credential Manager) or encrypt the file with a passphrase.

### SQL passthrough without confirmation

`relm` executes the SQL exactly as the user writes it. `DROP TABLE`, `TRUNCATE`, or `UPDATE ... WHERE` without a condition run without asking for confirmation.

- **Why:** the user is the one writing the SQL and knows the database they're connecting to. Keyword-based confirmations would be a fragile and annoying heuristic (see LESSONS L-09).
- **Mitigation:** `Read-only` mode (SQLite) as a safety net for production databases; the UI clearly shows which database you're connected to in the header.
- **Backlog (optional):** global `--read-only` flag that forces read-only mode in all engines.

### Only the first statement is executed

The editor only executes the first statement in the buffer (separated by `;`) and shows a warning. This avoids the kind of accidents of `multiStatements=true` (chaining destructive statements).

### MySQL/MariaDB: `multiStatements` disabled

The DSN never includes `multiStatements=true`. An SQL string with `;` doesn't become multiple statements.

### Identifiers always escaped

Table/column names are escaped with each engine's `QuoteIdent` dialect (`"x"`, `` `x` ``, `[x]`). Pagination `LIMIT`/`OFFSET` use integers generated by the browser, not user input. The editor SQL, on the other hand, is deliberately free: `relm` doesn't rewrite it.

## Hardening implemented (v0.1.0)

- **`ConnectionConfig.ReadOnly`** — opens SQLite with `mode=ro` (no WAL or `busy_timeout`). A write returns a driver error. Persisted in saved connections.
- **`ConnectionConfig.SSLMode`** — PostgreSQL sets `sslmode` (`prefer` by default; `require`, `verify-ca`, `verify-full`, `disable`). Persisted in saved connections.
- Validation of the `SSL` field in the form: invalid values prevent connecting.

## Security backlog

Ordered by impact:

1. **OS keychain** for saved passwords (removes the plaintext tradeoff).
2. **Global `read-only` flag/option** that applies to all five engines, not just SQLite.
3. **TLS options for MySQL/MariaDB and SQL Server** (not exposed today; they use the driver default).
4. **Query execution timeout** (today there's only a 5s connection timeout; a hung query shows an indefinite spinner).
5. **Persisted query history** — if added, make sure it doesn't include passwords (risk of queries with inline credentials).

## What `relm` is NOT

- It's not a server and doesn't expose ports.
- It doesn't validate roles or permissions: it uses the credentials you pass it as-is.
- It doesn't encrypt traffic by itself: connection security depends on the engine configuration and the `SSL` field.
